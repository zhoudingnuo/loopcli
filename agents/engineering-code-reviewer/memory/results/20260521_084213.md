## 1. 代码可读性与可维护性

### 🟡 server.py：WebUIHandler 职责过重（建议拆分）

`WebUIHandler` 承担了路由分发、CORS 处理、SSE 管理、业务逻辑、请求校验等所有职责，已超过 400 行。

**现状**：
```python
class WebUIHandler(SimpleHTTPRequestHandler):
    def do_GET(self):     # 手动 if/elif 路由链
    def do_POST(self):    # 手动 if/elif 路由链
    def _handle_sse_logs(self):      # SSE 逻辑 50+ 行
    def _handle_create_task(self):   # 业务逻辑
    def _handle_agent_start(self):   # 进程管理
    ...
```

**建议**：引入路由表模式，将 handler 拆分为独立函数或类：
```python
ROUTES = {
    ("GET", "/api/agents"): handle_list_agents,
    ("GET", "/api/tasks"): handle_list_tasks,
    ("POST", "/api/tasks"): handle_create_task,
    ...
}
```

**影响**：当前可维护，但随着 API 数量增长，if/elif 链会成为维护负担。

### 🟡 run.py：handle_event 复杂度偏高

`handle_event`（第 244-293 行）有 4 层嵌套的条件分支，处理 5 种事件类型。每种类型的处理逻辑差异较大，但都挤在一个函数里。

**建议**：按事件类型拆分为 `handle_assistant_event`、`handle_tool_result_event` 等，或使用字典分发。

### 💭 命名一致性

- server.py 用 `_safe_agent_path` 前缀 `_` 表示内部函数 — 一致且合理
- run.py 的 `cmd_task_inner` 命名暗示"内部"，但实际是被 `cmd_create` 复用 — 可考虑命名为 `append_task_to_agent` 更准确

## 2. 错误处理完整性

### 🟡 _read_body() 静默吞掉 JSON 解析错误

server.py 第 268-270 行：
```python
except (json.JSONDecodeError, UnicodeDecodeError):
    return {}
```

当请求体不是合法 JSON 时，返回空字典 `{}`。这意味着下游 handler 收到一个"看起来合法但没有字段"的 body，可能产生误导性行为（比如 `_handle_create_task` 会返回 "title is required" 而非 "malformed JSON"）。

**建议**：返回 `None` 并让调用方返回 400 Bad Request，与 body 为 `None` 的处理路径统一。

### 🟡 run_agent() 中 state.json 更新的健壮性

run.py 第 362-377 行：state.json 更新使用了 `json.load` + `json.dump` 的 read-rewrite 模式，虽然有文件锁保护，但如果 `json.load` 因为文件被外部截断而失败，会回退到空字典 `{}`，丢失之前的 `created`、`agent` 等字段。

**建议**：失败时保留已有字段，只更新 `status`/`last_run`/`run_count`：
```python
state = {"agent": name, "status": "idle", ...}  # 保留关键默认值
```

### 💭 git_push() 异常处理粒度

run.py 第 415-416 行：`except Exception as e` 捕获所有异常，包括 `KeyboardInterrupt` 以外的所有错误。可以更细粒度地区分网络超时、认证失败、文件锁定等不同场景，给出更有用的错误信息。

## 3. 性能瓶颈

### 🟡 SSE 日志轮询读取效率

server.py 第 336-341 行：SSE 每 1 秒调用 `get_recent_lines(log_path, 500)` 读取最后 500 行，而 `get_recent_lines` 会读取**整个文件**再取尾部。

```python
def get_recent_lines(filepath: Path, n=100):
    with open(filepath, "r", encoding="utf-8", errors="replace") as f:
        lines = f.readlines()  # 读取整个文件！
    return [l.rstrip("\n\r") for l in lines[-n:]]
```

如果日志文件增长到数 MB，每个 SSE 连接每秒都完整读一次，10 个连接就是每秒 10 次完整读取。

**建议**：
- 维护 `last_line_count`，只读取新增行
- 或使用 `seek()` 从上次位置继续读

### 💭 scan_agents() 同步 I/O

server.py 的 `scan_agents()` 遍历所有 agent 目录，逐个读取 state.json、SOUL.md、tasks.json。如果 agent 数量增长（比如 50+），同步读取会导致 `/api/agents` 响应变慢。

**现状可接受**：当前 agent 数量少，不会有实际问题。如果未来 agent 数量增长，考虑缓存或异步扫描。

## 4. API 设计一致性

### 🟡 路由风格不一致

| 端点 | 风格 | 问题 |
|------|------|------|
| `GET /api/agents` | RESTful | 正确 |
| `GET /api/tasks?agent=X` | 查询参数 | 正确 |
| `GET /api/agents/{id}/tasks` | RESTful 嵌套 | 与上面功能重复 |
| `POST /api/agents/start` | 动作在路径 | 非 RESTful |
| `POST /api/loopcli/start` | 动作在路径 | 非 RESTful |
| `POST /api/loopcli/dispatch` | 动作在路径 | 非 RESTful |

**建议**：统一风格。两种方案：
- **方案 A**：全 RESTful — `POST /api/agents/{id}/start`、`POST /api/loopcli/{id}/restart`
- **方案 B**：全 RPC — `POST /api/actions/start-agent`、`POST /api/actions/start-loopcli`

不必现在改，但新增 API 时应遵循统一风格。

### 🟡 认证覆盖不完整

server.py 第 407-413 行：`do_POST` 使用 `_write_semaphore` 和 `_require_auth`，但 `do_GET` 没有认证检查。这意味着所有数据（agent 状态、任务、日志）都可以未认证访问。

**现状评估**：如果 WebUI 只在本地运行（`127.0.0.1`），这不是安全问题。如果未来暴露到网络，GET 端点也需要认证。

### 💭 响应格式微调

- 错误响应格式统一为 `{"error": "..."}` — 很好
- 成功响应格式不统一：有时返回完整对象（如 `state`），有时返回包装对象（如 `{"status": "stopped"}`），有时返回列表
- 建议但不紧急：为 API 响应定义统一的信封格式

## 5. 代码重复与抽象机会

### 🔴 server.py 和 run.py 之间大量重复逻辑

这是**最值得关注的架构问题**。两个文件独立实现了相同的功能，没有共享层：

| 功能 | server.py | run.py |
|------|-----------|--------|
| JSON 读写 | `read_json()` + `write_json()` (第 46-58 行) | `load_agent_state()` + `load_agent_tasks()` + 内联 `json.dump` (第 77-91 行, 第 196-197 行) |
| Agent 发现 | `scan_agents()` (第 72-106 行) | `discover_agents()` (第 54-62 行) |
| 任务创建 | `_handle_create_task()` (第 452-472 行) | `cmd_task_inner()` (第 179-198 行) |
| 消息写入 | `_handle_message_send()` (第 601-626 行) | `cmd_msg()` (第 576-587 行) + `cmd_run()` 中的用户输入 (第 489-496 行) |
| Agent 启用/禁用 | `_handle_agent_enable()` (第 628-651 行) | `cmd_enable()` + `cmd_disable()` (第 537-559 行) |
| Agent 路径验证 | `_safe_agent_path()` (第 61-69 行) | 无（直接拼接路径） |

**风险**：修改一个功能时可能忘记同步另一处，导致行为不一致。例如：
- server.py 有 `_safe_agent_path` 防路径遍历，run.py 没有
- server.py 有 `_json_lock` 防并发写，run.py 用 `msvcrt` 文件锁
- 两者实现不同的 agent 过滤逻辑

**建议**：提取 `loopcli_lib.py` 共享模块：
```python
# loopcli_lib.py
def read_json(path, default=None): ...
def write_json(path, data): ...
def safe_agent_path(agent_id): ...
def discover_agents(): ...
def create_task(agent_id, title, desc): ...
def send_message(agent_id, content, sender): ...
```

### 🟡 server.py 内部重复：任务 ID 生成

第 461 行和第 566 行：
```python
new_id = max((t.get("id", 0) for t in tasks), default=0) + 1
```

出现两次，完全相同。如果未来改为 UUID 或数据库自增，需要改两处。

**建议**：提取为 `next_task_id(tasks)` 函数。

### 🟡 run.py 内部重复：消息格式化

`cmd_msg()`（第 586 行）、`cmd_run()` 的用户输入（第 494-495 行）、以及 `server.py` 的 `_handle_message_send()`（第 623-624 行）都使用相同格式的 markdown 消息模板。

## 6. 跨文件架构问题

### 🟡 硬编码配置

两个文件都硬编码了 `D:\loopcli`：
- server.py 第 22 行：`LOOPCLI_ROOT = Path(r"D:\loopcli")`
- run.py 第 12 行：`LOOPCLI_DIR = r"D:\loopcli"`

**建议**：通过环境变量或配置文件统一管理：
```python
LOOPCLI_ROOT = Path(os.environ.get("LOOPCLI_ROOT", r"D:\loopcli"))
```

### 💭 平台锁定

- run.py 使用 `msvcrt`（Windows 专用文件锁）
- server.py 使用 `subprocess.CREATE_NO_WINDOW`（Windows 专用）
- 路径使用反斜杠

当前项目明确只在 Windows 上运行，不是问题。但如果未来需要跨平台，建议抽象平台相关代码。

### 💭 缺少配置验证/启动检查

server.py 和 run.py 启动时都不验证依赖是否就绪（如 `LOOPCLI_ROOT` 是否存在、claude 命令是否可用）。如果环境有问题，会在运行时才报错，且错误信息可能不够清晰。
